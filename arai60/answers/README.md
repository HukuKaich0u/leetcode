# arai60 answers

このディレクトリは、LeetCode の AC コード置き場ではなく、`arai60` を通して基礎体力を鍛えるための回答集です。

鍛えたい軸は次の 3 つです。

- `Rustを書く力`
- `いいコードを書く力`
- `アルゴリズムとデータ構造の力`

`面接で説明できる` は最低ラインです。主目的は、それより一段深く、問題の本質を抽象化し、複数の解法を比較し、Rust で破綻なく実装し、テストで理解を固められるようにすることです。

## このディレクトリで目指すもの

各 `.rs` は次を満たす教材にします。

- 何を学ぶ問題かが最初に分かる
- 問題の本質を自分の言葉で説明できる
- 複数解法を比較して、本命を選んだ理由を語れる
- 同じ解法でも、コードの組み立て方の違いを比較できる
- Rust 実装を読んで、書き方の意図まで理解できる
- テストを通して境界条件や罠ケースを確認できる

つまり「答え」ではなく、「答えに至る思考と、それを Rust でどう表現するか」を残します。

## 各回答ファイルの必須構成

各問題ファイルは、少なくとも次の要素を持たせます。

1. `この問題で鍛えること`
2. `問題の本質`
3. `解法候補`
4. `採用解法の説明`
5. `Rust実装`
6. `別解`
7. `Rust観点の解説`
8. `いいコード観点の解説`
9. `落とし穴`
10. `テスト`

以下、それぞれの見出しで何を書くかを定義します。

### 1. この問題で鍛えること

最初に、この問題が何を練習するためのものかを明示します。最低限、次の 3 軸は書きます。

- 学ぶアルゴリズム
- 学ぶデータ構造
- Rust での練習ポイント

必要なら、次も追加します。

- どんな抽象化が見抜きどころか
- 実務コードにも通じる設計感覚は何か

ここを読むだけで、「この問題を解く意味」が分かる状態にします。

### 2. 問題の本質

問題文を言い換えるだけでは不十分です。何を見抜けば解きやすくなるかを書きます。

例:

- 配列問題に見えるが、本質は `prefix sum`
- 文字列問題に見えるが、本質は `unweighted graph` の最短路
- 制約が小さくないので、素直な全探索は捨てるべき
- 単調性があるので、二分探索に持ち込める

ここでは次を明確にします。

- 入力をどうモデル化するか
- 制約のどこが解法選択を支配するか
- 何を状態として持つべきか
- どの観察が突破口になるか

### 3. 解法候補

本命解法だけを書くのではなく、候補になる解法を並べて比較します。各候補に最低限、次を書きます。

- 考え方
- 時間計算量
- 空間計算量
- 主に使うデータ構造
- 採用理由 / 非採用理由

目的は「知っている解法を 1 個出す」ことではなく、「複数案から選べる」状態を作ることです。

### 4. 採用解法の説明

本命解法は厚めに説明します。次のような観点を重視します。

- なぜその見方で問題を解けるのか
- どんな状態や不変条件を保つのか
- ループや探索が進むたびに何が保証されるのか
- どの時点で答えが確定するのか
- 正しさをどう直感的に説明できるか

問題によっては、さらに次も書きます。

- 単調性
- greedy choice の正当化
- DP の状態設計と遷移理由
- `HashMap` / `BinaryHeap` / `VecDeque` / `Union-Find` などの採用理由

ここは「なぜ解けるのか」を理解する中心です。

### 5. Rust実装

本命解法の `impl Solution` を置きます。実装は、ただ通るだけではなく、読みやすさと説明可能性を意識します。

基本方針:

- `use` は必要最小限にする
- 変数名は役割が伝わるものにする
- ループや分岐の意図が追いやすい形にする
- 補助関数を切るなら責務を明確にする
- 面接でも実務でも読みやすい、素直な実装を優先する

### 6. 別解

比較用の別解を `1〜2 個` 置きます。別解も実際にコードにします。

各別解について、短く次を書きます。

- どんな発想か
- どんなときに有力か
- なぜ今回は本命にしなかったか
- 本命と比べたときの実装上のトレードオフは何か

別解は飾りではありません。比較して理解を深めるためのものです。

### 7. Rust観点の解説

アルゴリズム説明だけで終わらせず、Rust でどこが学びどころかを明示します。

例:

- `iter()` / `into_iter()` / `iter_mut()` の使い分け
- 所有権と借用の扱い
- `HashMap` / `HashSet` / `VecDeque` / `BinaryHeap` の使いどころ
- 添字アクセスと境界条件の管理
- `Option` を使った分岐の整理
- 再帰を書くときの所有権や参照の設計

ここでは「この書き方が Rust で自然な理由」を説明します。

### 8. いいコード観点の解説

アルゴリズムの正しさだけでなく、コード品質も対象にします。

例:

- 命名が問題の概念と一致しているか
- 1 つの関数やループに責務を詰め込みすぎていないか
- 境界条件が読みやすい形で処理されているか
- 早期 return が意図を明確にしているか
- テストしやすい構造になっているか

「通るコード」と「保守しやすいコード」の差を言語化することが重要です。

### 9. 落とし穴

その問題で典型的にハマる点を明示します。

例:

- off-by-one
- 重複要素の扱い
- `visited` の更新タイミング
- overflow / underflow
- 空配列、長さ 1、到達不能ケース
- ソート後に元 index を失う問題

ここは「次に同じミスをしない」ためのメモです。

### 10. テスト

各 `.rs` ファイルの中に `#[cfg(test)]` を置いて、同じファイル内で完結させます。

最低限、次は入れます。

- 基本ケース
- 境界ケース
- 罠ケース

別解があるなら、本命と同じ観点で検証します。

## 複数解法の扱い方

各問題は、原則として次の構成にします。

- `本命解法 1 個`
- `比較用の別解 1〜2 個`

各解法に対して、少なくとも次を残します。

- どう考えるか
- どのデータ構造を使うか
- 時間計算量 / 空間計算量
- 採用理由 / 非採用理由

さらに、可能な限り `コードのレベル差` も見せます。

- `素朴実装`
メソッドを少なめにし、まずは自前で愚直に書く版です。考え方をそのままコードへ落とす練習に使います。

- `本命実装`
面接でも実務でも説明しやすい形に整理した版です。これを主役にします。

- `整理した実装`
何回も使う処理を関数へ切り出し、責務を少し分けた版です。どこから切り出すと読みやすくなるかを学びます。

本命は「最も強い理論上の解法」ではなく、次のバランスが最もよいものを優先します。

- 本質を学びやすい
- 面接で説明しやすい
- Rust で素直に書ける
- バグりにくい

## Rust 実装コメントの方針

コメントは多ければよいわけではありません。理解の節目にだけ置きます。

### コメントを書く場所

- メソッドの直前
- 重要な処理ブロックの直前
- Rust 特有で詰まりやすい箇所
- 補助関数の役割説明

### コメントに書くこと

- この処理ブロックの意図
- ここで保ちたい不変条件
- なぜこのデータ構造を使うか
- Rust 的に迷いやすいポイント

### 避けること

- コードを日本語に言い換えただけのコメント
- 1 行ごとの実況
- 本文の解説と重複する長文

### コメントの例

```rust
use std::collections::HashMap;

impl Solution {
    pub fn two_sum(nums: Vec<i32>, target: i32) -> Vec<i32> {
        // seen[value] = その値を見た index。
        // 各要素について、必要な相方がすでに出たかだけを確認すればよい。
        let mut seen = HashMap::new();

        for (i, &value) in nums.iter().enumerate() {
            let need = target - value;
            if let Some(&j) = seen.get(&need) {
                return vec![j as i32, i as i32];
            }

            // 現在の値は、後続要素にとっての相方候補になる。
            seen.insert(value, i);
        }

        vec![]
    }
}
```

## テストの方針

テストは「AC したことの確認」ではなく、「仕様を理解しているかの確認」として書きます。

各問題で最低限見る観点:

- 基本例が通る
- 最小入力や空入力などの境界が通る
- 間違えやすいケースが通る
- 別解も同じ仕様で通る
- コードレベル違いの実装も同じ仕様で通る

問題によっては、次も積極的に入れます。

- 重複
- 負数
- ソート済み / 未ソート
- 到達不能
- 深い木 / 長いリスト
- 破壊的更新の有無

## 良い回答と悪い回答

### 良い回答

- 何を学ぶ問題かが最初に分かる
- 問題の本質の見抜き方が書かれている
- 複数解法の比較がある
- コードレベルの比較がある
- 本命解法の採用理由がある
- Rust 実装が読みやすい
- コメントが意図を支えている
- テストがある

### 悪い回答

- AC コードだけが置かれている
- 使わない `use` が大量にある
- 「なぜ」がなく、「どう書いたか」しかない
- 別解がなく、比較して学べない
- 同じ解法をどう整理していくかが見えない
- Rust で詰まりやすい点が放置されている
- テストがない

## 執筆チェックリスト

回答を書くときは、最低限次を確認します。

- この問題で鍛えることが最初に書かれているか
- 問題の本質を、自分の言葉で抽象化できているか
- 候補解法を比較して、本命の採用理由を書いたか
- 本命解法の理屈を、不変条件や状態まで踏み込んで説明したか
- 本命の Rust 実装を書いたか
- 素朴実装 / 本命実装 / 整理した実装のどこまで見せるか判断したか
- 別解を 1〜2 個コードで示したか
- Rust 観点の学びを書いたか
- コード品質の観点を書いたか
- 落とし穴を書いたか
- `#[cfg(test)]` で基本・境界・罠ケースを押さえたか
- `use` は必要最小限か
- コメントは意図とつまずきどころに絞れているか

## 最後に

この回答集は、「問題を解けるようになる」ためだけのものではありません。

- 抽象化して考える
- 複数案を比較して選ぶ
- Rust で自然に書く
- 読みやすく壊れにくい形に整える
- テストで理解を確かめる

この流れを毎問で繰り返し、`arai60` をアルゴリズム演習ではなく、エンジニアとしての基礎訓練に変えていきます。
