# arai60 answers README redesign

## Goal

`arai60/answers/README.md` を単なるディレクトリ説明ではなく、各回答ファイルの品質基準と執筆フォーマットを定義する仕様書に作り替える。

主目的は次の 3 つを同時に鍛える教材にすること。

- Rust を使って破綻なく書く力
- いいコードを書く力
- アルゴリズムとデータ構造の力

この 3 つを別々に扱うのではなく、各問題で同時に訓練する。

## Positioning

各 `.rs` は単なる AC コード置き場ではない。

- 問題を抽象化して本質を説明できる
- 複数解法を比較して採用理由を語れる
- Rust で自然に実装できる
- テストで理解の抜けを確認できる

という 4 点を満たす教材にする。

「面接で説明できる」は最低ラインにとどめる。README の主軸は、面接対策に閉じない形で、強いエンジニアになるための基礎を固めることに置く。

## Reader outcome

README を読んだ人は、各回答ファイルを次のように仕上げるべきだと分かる状態にする。

- 何を学ぶ問題かを先に定義する
- 問題をどう抽象化するかを言語化する
- 解法候補を比較し、本命を選ぶ理由を説明する
- Rust 実装を、動くだけでなく読みやすく書く
- テストで基本ケース、境界ケース、罠ケースを押さえる

## README structure

README は少なくとも次の章を持つ。

1. このディレクトリの目的
2. 何を鍛える教材か
3. 各 `.rs` に必須の構成
4. 複数解法の扱い方
5. Rust 実装コメントの方針
6. テストの方針
7. 良い回答 / 悪い回答の例
8. 執筆時のチェックリスト

## Required file format

各回答ファイルは以下を必須要素とする。

1. `この問題で鍛えること`
2. `問題の本質`
3. `解法候補`
4. `採用解法の説明`
5. `Rust実装`
6. `別解`
7. `Rust観点の解説`
8. `いいコード観点の解説`
9. `落とし穴`
10. `テスト`

### 1. この問題で鍛えること

最低でも次の 3 軸を書く。

- 学ぶアルゴリズム
- 学ぶデータ構造
- Rust での練習ポイント

必要なら追加で次も書く。

- 問題をどう抽象化するか
- 実務コードにも通じる設計感覚

### 2. 問題の本質

問題文の要約ではなく、何を見抜けば解きやすくなるかを書く。

例:

- 配列問題に見えるが本質は prefix sum
- 文字列問題に見えるが本質は graph shortest path
- 制約から全探索が不可能で、単調性を使う必要がある

ここでは次を明確にする。

- 入力をどうモデル化するか
- 制約のどこが解法選択を支配するか
- 何を状態として持つべきか

### 3. 解法候補

本命だけでなく、候補になる解法を 2〜3 個並べる。

各候補に最低限書くもの:

- 考え方
- 時間計算量
- 空間計算量
- 主に使うデータ構造
- 採用 / 非採用理由

この章の目的は、「この解法を知っている」ではなく「比較して選べる」状態を作ること。

### 4. 採用解法の説明

本命解法の理屈を厚めに書く。

最低限含める論点:

- なぜその見方で問題を解けるのか
- 状態や不変条件は何か
- ループや探索の進行で何が保証されるか
- どの時点で答えが確定するか
- 正しさを直感的にどう説明するか

必要なら次も含める。

- 単調性
- greedy choice の正当化
- DP の状態設計と遷移理由
- union-find / heap / deque / hash map などの採用理由

### 5. Rust実装

本命解法の `impl Solution` を置く。

実装は次を満たす。

- 必要最小限の `use`
- 変数名が役割を表す
- 分岐やループの意図が追いやすい
- 補助関数は責務が明確
- 面接でも実務でも読める程度に素直

### 6. 別解

比較用の別解を 1〜2 個置く。

形は柔軟だが、少なくとも本命と衝突しないように別 struct や補助関数名で分ける。

各別解にも短く次を書く。

- どんなときに有力か
- なぜ今回は本命にしなかったか
- 実装上のトレードオフ

### 7. Rust観点の解説

Rust ならではの学びを抜き出して書く。

対象例:

- 所有権と借用
- `iter()` / `into_iter()` / `iter_mut()` の選択
- `HashMap` / `HashSet` / `BinaryHeap` / `VecDeque` の使い方
- 添字アクセスと境界管理
- `Option` を使う分岐の整理
- 再帰と所有権の扱い

ここでは「なぜこの書き方が Rust で自然か」を説明する。

### 8. いいコード観点の解説

アルゴリズムの正しさだけでなく、コード品質も説明対象にする。

論点例:

- 命名が問題の概念と一致しているか
- 1 つのループや関数に責務を詰め込みすぎていないか
- 境界条件の扱いが読みやすいか
- 早期 return が意図を明確にしているか
- 将来テストや修正を入れやすい構造か

「通るコード」と「保守しやすいコード」の差を言語化する。

### 9. 落とし穴

典型バグや誤解しやすい論点を列挙する。

例:

- off-by-one
- 重複要素の扱い
- visited の更新タイミング
- overflow / underflow
- ソート後に元 index を失う問題
- 空配列や長さ 1 の扱い

### 10. テスト

各 `.rs` 内に `#[cfg(test)]` を置く。

最低限テストするもの:

- 基本ケース
- 境界ケース
- 罠ケース

本命解法と別解があるなら、可能な限り同じ観点で両方を検証する。

## Depth standard

解説は「面接で一言しゃべれる程度」では不十分。

目指す深さは次。

- 問題の本質を抽象化できる
- 解法の選定理由を比較で説明できる
- 不変条件や正しさの直感を語れる
- Rust 実装の要点を読み解ける
- コード品質の観点で改善点を見抜ける

各問題は「なぜ解けるか」と「なぜその書き方にするか」の両方を学ぶ場にする。

## Rust comment policy

コードコメントは多ければよいわけではない。README では次を規約化する。

### コメントを書く場所

- メソッドの直前
- 重要な処理ブロックの直前
- Rust 特有で詰まりやすい箇所
- 補助関数の役割説明

### コメントに書くこと

- この処理ブロックの意図
- ここで保ちたい不変条件
- なぜこのデータ構造を使うか
- Rust 的に迷いやすいポイント

### 避けること

- コードを日本語に言い換えただけのコメント
- 1 行ごとの実況
- 本文の解説と重複する長文

### Example style

```rust
impl Solution {
    pub fn two_sum(nums: Vec<i32>, target: i32) -> Vec<i32> {
        // seen[value] = その値を見た index。
        // 各要素について、必要な相方が過去にあるかだけを確認する。
        let mut seen = HashMap::new();

        for (i, &value) in nums.iter().enumerate() {
            let need = target - value;
            if let Some(&j) = seen.get(&need) {
                return vec![j as i32, i as i32];
            }

            // 現在の値は、後続要素にとっての相方候補になる。
            seen.insert(value, i);
        }

        vec![]
    }
}
```

## Test policy

各問題で `#[cfg(test)]` を使い、実装と同じファイルでテストを完結させる。

README では次を要求する。

- 基本例が通る
- 最小入力や空入力などの境界が通る
- 間違えやすいケースが通る
- 別解があるなら同じ仕様で検証する

問題に応じて追加で検討する観点:

- 重複
- 負数
- ソート済み / 未ソート
- 到達不可
- 深い木 / 長いリスト
- 破壊的更新の有無

## Good vs bad answers

README では良い回答と悪い回答の差を明記する。

### 良い回答

- 何を学ぶ問題かが最初に分かる
- 本質の見抜き方が書かれている
- 解法比較がある
- 採用理由がある
- Rust 実装が読みやすい
- コメントが意図を支えている
- テストがある

### 悪い回答

- AC コードだけ
- 使わない `use` が大量にある
- 「なぜ」がなく、「どう書いたか」しかない
- 別解がなく比較できない
- Rust のつまずきどころが放置されている
- テストがない

## Writing rules

README の運用ルールとして次を定義する。

- 解説は詳しく書く。ただし冗長にしない
- まず問題の抽象化を書く
- 実装は本命を 1 つ主役にする
- 別解は比較材料として置く
- 各解法に計算量とデータ構造を書く
- Rust コメントは意図とつまずきどころに絞る
- `use` は必要最小限にする
- テストは仕様理解の確認手段として書く

## Rollout implication

README を更新した後の全問題リライトは、README の必須構成に沿って統一する。

期待される変化:

- 解説の粒度が揃う
- Rust 実装の質が揃う
- テスト方針が揃う
- 学習教材として再利用しやすくなる
